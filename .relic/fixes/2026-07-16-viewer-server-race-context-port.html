Fix: duplicate viewer servers from MCP race; context blind to auto-incremented port

ID: 2026-07-16-viewer-server-race-context-port Date: 2026-07-16 Spec: 012-spec-viewer Status: solved Classification: code-bug

Issue

Two related lifecycle defects found while smoke-testing relic mcp on this repo:

  • Back-to-back MCP tool calls (view_spec + list_views — the normal client pattern) each ran ensureServer concurrently; both probes saw no server, both spawned relic serve. Result: two servers (4747 + 4748), and the second overwrote viewer.json, so the URL returned to the user disagreed with the recorded lifecycle state.
  • relic context probed only the configured port, so whenever the server auto-incremented (port taken), context reported running: false, url: null for a healthy viewer.

Root Cause

code-bug — the probe-then-spawn sequence in mcp.ts ensureServer was not serialized across concurrent tool calls (classic TOCTOU), and context.ts derived the probe port from config.json alone, ignoring the runtime port the server records in viewer.json.

Changes

Verified live from clean state: the same concurrent call pattern now yields exactly one listener with URL, viewer.json, and relic context all agreeing; with the default port occupied by a foreign process, context reports the auto-incremented server as running.
