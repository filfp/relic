Delivered

Hierarchical federated knowledge across nested projects

Relic lets a monorepo consult and confront its own documentation together with the independently owned knowledge of explicitly selected nested projects. Each project remains a complete Relic boundary when used on its own, including any federation that project explicitly declares.

Delivered: core composition, CLI search, HTTP transport, artifact authority, viewer navigation, and the conditional central-skill reference implement this contract while preserving the existing single-project shape when federation is absent.

Problem

A monorepo may contain global specifications, notes, decisions, and operational knowledge while nested repositories or submodules represent independently usable products. A backend needs its own topology and knowledge when opened alone, but the monorepo needs one aggregate view when work starts from the monorepo root.

The same need exists without nested Git repositories. A product may contain packages that require independent documentation and governance boundaries, while the product itself is later composed into a larger monorepo. Federation models Relic project boundaries, not repository or submodule boundaries.

Pointing the parent topology directly at every child corpus would reinterpret child knowledge under parent-owned record kinds. Searching recursively for descendant relic.yaml files would silently include fixtures, vendors, examples, or unrelated checkouts. Federation therefore composes explicit project read models; it does not absorb or autodiscover them.

Selected boundary

The nearest project-local, regular, non-symlinked relic.yaml found from the working directory selects the complete Relic boundary for that invocation. Relic never walks above it looking for a parent federation.

Working directoryKnowledge boundary
Monorepo root The root corpus plus every valid project reachable through explicitly declared federation members.
Nested backend The backend corpus and its explicitly reachable federation subtree, never an ancestor or sibling tree.
Standalone clone of a member That project's corpus and only the federation subtree it explicitly declares.

This boundary is both an ownership rule and a level-of-work rule. Moving to the monorepo root is the explicit act that selects global knowledge.

Configuration

A project's topology continues to declare its required specification, shared, and record roots. The optional sibling federation object composes independent Relic projects without turning them into corpus roots. When an explicitly reached member declares its own federation, traversal continues through that member's explicit declarations. 

topology:
  specs: .relic/specs
  shared: .relic/shared
  records:
    note: docs/notes
federation:
  members:
    backend: services/backend
    frontend: apps/frontend
    mobile: apps/mobile

If services/backend/relic.yaml independently declares a package member, the monorepo reaches it through the two explicit edges and addresses it hierarchically: 

federation:
  members:
    domain: packages/domain

# Address from the monorepo view: root/backend/domain
  • Omitting federation preserves current single-project behavior.
  • members is an explicit map of lowercase kebab-case local keys to project directories.
  • root is reserved as the selected project's first transport-address segment.
  • Each member path is relative to and contained by the project that declares it.
  • Each member directory contains its own regular, non-symlinked relic.yaml.
  • A member may be a package or directory with its own Relic boundary; it need not be a Git repository or submodule.
  • Traversal follows federation.members recursively across reached projects.
  • An undeclared descendant relic.yaml has no effect.

Knowledge remains project-owned

Every project keeps the minimum Relic topology of specifications, shared knowledge, and project-declared record kinds. Specifications remain important anchors without imposing a specification-driven workflow. Notes, postmortems, incidents, runbooks, discussions, and compound kinds such as backend-postmortem use the same open record mechanism.

  • A member's relic.yaml alone defines that member's roots and record kinds.
  • A member's federation declarations remain part of its boundary when another project composes it.
  • Federation membership does not transfer document or governance ownership to the root.
  • Root knowledge has no automatic semantic precedence over member knowledge.
  • Contradictions across projects remain evidence for confrontation, not automatic reconciliation.
  • The same physical content may intentionally be consumed by multiple project topologies.
  • Content overlap across project topologies is not diagnosed, deduplicated, or assigned a global owner.

Federated skill behavior

The central skill reads its federation reference only when the selected relic.yaml declares federation. It begins from the developer's target and expands progressively through root or member knowledge as relevance requires; it does not load every corpus as a precondition or require Relic search.

  • The skill may confront related or contradictory knowledge across any reachable project.
  • Member-key paths identify context; they do not establish authority or document identity.
  • The skill recommends updates in the project that owns each affected document.
  • One developer authorization may name coordinated writes in the root and multiple members.
  • No command, agent, or root project silently synchronizes or mutates member knowledge.

Command behavior

OperationBehavior
relic search Search the selected corpus and every valid project transitively reached through explicit federation declarations.
relic serve Present the same composed read model grouped by hierarchical project address.
relic init Create only the selected project's minimal topology; never initialize members.
relic install Install only for the selected project; never traverse federation membership.

Federation adds no command, mode, session, manifest, synchronization engine, or persisted cache. Search, serve, and their HTTP API remain read-only; this does not restrict developer-authorized skill authoring across project boundaries.

Composed read model and addressing

Federation composes separate project read models rather than flattening their documents into one path or identity space. A federated project address is the ordered path of local member keys from the selected root and never becomes authored document metadata. 

{
  "project": ["root", "product", "api"],
  "path": "docs/decisions/ADR-001-retry-policy.md",
  "id": "ADR-001"
}
  • id remains the member-owned document identity.
  • path remains relative to the owning project.
  • project starts with root and appends one local member key for each explicit federation edge.
  • The same nested project has a shorter view-local address when selected from inside its own subtree.
  • The project address is never prepended to the ID or persisted in the document.
  • Equal IDs or paths in different projects do not conflict.
  • Equal local member keys under different parents do not conflict.
  • Search results, summaries, routes, artifacts, and diagnostics retain the complete project address.
  • Federated document and content routes resolve the validated tuple {project, path}.
  • Unknown project-address segments do not become filesystem paths and return not found.
  • A project without federation retains existing single-project response shapes.

Configuration duplicates

Duplicate federation reachability is configuration ambiguity, unlike intentional overlap between independently owned corpus topologies.

  • No project can declare itself as a member.
  • A project realpath reached through multiple direct or nested paths is loaded once.
  • The shortest valid project address wins; equal-depth addresses are ordered lexically.
  • Noncanonical aliases and repeated realpaths produce focused diagnostics on their declaring edges.
  • Traversal never revisits a realpath, so repeated or cycle-like branches terminate locally.
  • Normalization prevents duplicate project entries in search and serve.
  • Diagnostics appear in the federation maintenance view without hiding valid knowledge.

Top-down links

Federation adds no custom link protocol. An ordinary relative link authored in an ancestor project may resolve to a canonical document or artifact in any reachable descendant. The composed view derives its backlink without rewriting either source.

  • An ancestor-to-descendant link may become canonical in a view containing both projects.
  • The derived cross-project backlink exists only in that federated view.
  • A nested project consulted alone retains its independent graph and federation subtree.
  • Descendant-to-ancestor and cross-branch links are not federated and cannot escape the selected subtree.

Failure isolation

FailureResult
Selected relic.yaml has invalid YAML or an unsafe authority The selected federation is unavailable and Relic does not fall back to an ancestor.
Local topology is invalid but federation membership is readable The local corpus is unavailable while valid members remain consultable.
One member entry is invalid Only that edge and descendants reachable solely through it are unavailable.
One member's relic.yaml is structurally unreadable That member and descendants discoverable only through it are unavailable, with an address-qualified diagnostic.
One member record entry is invalid That member preserves every other valid topology root.
A reached member has invalid local topology but readable federation membership Its local corpus is unavailable while its valid descendant projects remain consultable.
A member realpath is reached again The canonical project stays available and only the repeated edge is diagnosed and not traversed.
Knowledge changes while serve is running A later derived refresh reflects current files without persisted state.

Safety and performance

  • Every project is parsed and contained against its own project root.
  • Artifact delivery resolves only through a validated project address and that project's discovered artifacts.
  • Absolute member paths, boundary escapes, unsafe authorities, and unsafe artifact resolution fail locally.
  • Only projects reachable by following explicit federation edges from the selected root are loaded.
  • Each valid project is loaded at most once per derived refresh.
  • Process-local derived caching is allowed; persisted or authoritative cache state is not.
  • Aggregate ordering is stable by score, project-address segments, and project-relative path.
  • Federation remains localhost-only under the existing viewer security contract.

Acceptance evidence

  1. A project without federation preserves current selection, search, API, viewer, init, and install behavior.
  2. Running inside a member never consults an ancestor federation.
  3. Running at a federation root exposes every safe project transitively reachable through explicit member declarations.
  4. A package with its own relic.yaml can be a governed federation member without being a Git repository.
  5. Nested member keys produce stable hierarchical project addresses and remain local to their declaring parent.
  6. Fixtures retain the minimum specs and shared topology while exercising custom note and compound postmortem record kinds.
  7. Equal IDs and paths across projects remain independently addressable without derived IDs.
  8. Intentional corpus overlap across project topologies remains visible under each project without an ownership diagnostic.
  9. Duplicate or repeatedly reached member realpaths load once and produce localized edge diagnostics.
  10. The failure matrix preserves every safe valid corpus boundary.
  11. Ancestor-to-descendant links resolve canonically only in a composed view containing both projects; upward and cross-branch links remain bounded.
  12. Unknown address segments, path escapes, symlinked authorities, repeated traversal, and unsafe artifact requests cannot expose content.
  13. Search, API, viewer, and the conditional skill reference agree on project ownership and addressing.
  14. An explicitly authorized interaction can update named root and member documents without a federated mutation command.
  15. Performance evidence shows work bounded by the reachable explicit federation graph rather than filesystem size.

Deliberately deferred

  • Automatic discovery of descendant or ancestor relic.yaml files.
  • Projects outside the selected project boundary.
  • Descendant-to-ancestor and cross-branch federated links.
  • Global or derived document IDs.
  • Automatic cross-project writes, synchronization, reconciliation, or lifecycle governance.
  • A fifth CLI command or a second Relic configuration file.
