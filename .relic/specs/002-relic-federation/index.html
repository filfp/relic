Accepted direction

Federated knowledge and confrontation across nested projects

Relic will let a monorepo consult and confront its own documentation together with the independently owned knowledge of explicitly selected nested projects. Each project remains a complete Relic boundary when used on its own.

Not implemented: this specification records the accepted federation contract. The current CLI and read model remain single-project until implementation, tests, generated distributions, and the linked product contracts agree with it.

Problem

A monorepo may contain global specifications, notes, decisions, and operational knowledge while nested repositories or submodules represent independently usable products. A backend needs its own topology and knowledge when opened alone, but the monorepo needs one aggregate view when work starts from the monorepo root.

Pointing the parent topology directly at every child corpus would reinterpret child knowledge under parent-owned record kinds. Searching recursively for descendant relic.yaml files would silently include fixtures, vendors, examples, or unrelated checkouts. Federation therefore composes explicit project read models; it does not absorb or autodiscover them.

Selected boundary

The nearest project-local, regular, non-symlinked relic.yaml found from the working directory selects the complete Relic boundary for that invocation. Relic never walks above it looking for a parent federation.

Working directoryKnowledge boundary
Monorepo root The root corpus plus valid direct members declared by that root.
Nested backend Only the backend corpus and any federation declared by the backend itself.
Standalone clone of a member Only that project's own selected boundary.

This boundary is both an ownership rule and a level-of-work rule. Moving to the monorepo root is the explicit act that selects global knowledge.

Configuration

A project's topology continues to declare its required specification, shared, and record roots. The optional sibling federation object composes independent Relic projects without turning them into corpus roots. 

topology:
  specs: .relic/specs
  shared: .relic/shared
  records:
    note: docs/notes
federation:
  members:
    backend: services/backend
    frontend: apps/frontend
    mobile: apps/mobile
  • Omitting federation preserves current single-project behavior.
  • members is an explicit map of lowercase kebab-case keys to project directories.
  • root is reserved as the selected federation root's transport key.
  • Each member path is relative to and contained by the selected project root.
  • Each member directory contains its own regular, non-symlinked relic.yaml.
  • Only direct members participate; nested member federations are not traversed.
  • An undeclared descendant relic.yaml has no effect.

Knowledge remains project-owned

Every project keeps the minimum Relic topology of specifications, shared knowledge, and project-declared record kinds. Specifications remain important anchors without imposing a specification-driven workflow. Notes, postmortems, incidents, runbooks, discussions, and compound kinds such as backend-postmortem use the same open record mechanism.

  • A member's relic.yaml alone defines that member's roots and record kinds.
  • Federation membership does not transfer document or governance ownership to the root.
  • Root knowledge has no automatic semantic precedence over member knowledge.
  • Contradictions across projects remain evidence for confrontation, not automatic reconciliation.
  • The same physical content may intentionally be consumed by multiple project topologies.
  • Content overlap across project topologies is not diagnosed, deduplicated, or assigned a global owner.

Federated skill behavior

The central skill reads its federation reference only when the selected relic.yaml declares federation. It begins from the developer's target and expands progressively through root or member knowledge as relevance requires; it does not load every corpus as a precondition or require Relic search.

  • The skill may confront related or contradictory knowledge across visible projects.
  • Member keys identify context; they do not establish authority or document identity.
  • The skill recommends updates in the project that owns each affected document.
  • One developer authorization may name coordinated writes in the root and multiple members.
  • No command, agent, or root project silently synchronizes or mutates member knowledge.

Command behavior

OperationBehavior
relic search Search the selected root corpus and every valid direct member when federation is declared.
relic serve Present the same composed read model grouped by project.
relic init Create only the selected project's minimal topology; never initialize members.
relic install Install only for the selected project; never traverse federation membership.

Federation adds no command, mode, session, manifest, synchronization engine, or persisted cache. Search, serve, and their HTTP API remain read-only; this does not restrict developer-authorized skill authoring across project boundaries.

Composed read model and addressing

Federation composes separate project read models rather than flattening their documents into one path or identity space. A federated address is structured and never becomes authored document metadata. 

{
  "project": "backend",
  "path": "docs/decisions/ADR-001-retry-policy.md",
  "id": "ADR-001"
}
  • id remains the member-owned document identity.
  • path remains relative to the owning project.
  • project is a view-local address key and is never prepended to the ID.
  • Equal IDs or paths in different projects do not conflict.
  • Search results, summaries, routes, artifacts, and diagnostics retain the project key.
  • Federated document and content routes resolve the validated tuple {project, path}.
  • Unknown project keys do not become filesystem paths and return not found.
  • A project without federation retains existing single-project response shapes.

Configuration duplicates

Duplicate federation membership is configuration ambiguity, unlike intentional overlap between independently owned corpus topologies.

  • The selected project cannot declare itself as a member.
  • Two member paths resolving to the same project realpath are loaded once.
  • The first valid declared key addresses that project; later aliases produce focused diagnostics.
  • Normalization prevents duplicate member entries in search and serve.
  • Diagnostics appear in the federation maintenance view without hiding valid knowledge.

Top-down links

Federation adds no custom link protocol. An ordinary relative link authored in the selected root may resolve to a canonical document or artifact in a direct member. The composed view derives its backlink without rewriting either source.

  • Root-to-direct-member links may become canonical in the federated view.
  • The derived cross-project backlink exists only in that federated view.
  • A member consulted alone retains its independent graph.
  • Member-to-root and member-to-sibling links are not federated and cannot escape the member boundary.

Failure isolation

FailureResult
Selected relic.yaml has invalid YAML or an unsafe authority The selected federation is unavailable and Relic does not fall back to an ancestor.
Local topology is invalid but federation membership is readable The local corpus is unavailable while valid members remain consultable.
One member entry is invalid The root and every other valid member remain available.
One member's relic.yaml is invalid Only that member is unavailable, with a project-qualified diagnostic.
One member record entry is invalid That member preserves every other valid topology root.
Knowledge changes while serve is running A later derived refresh reflects current files without persisted state.

Safety and performance

  • Every project is parsed and contained against its own project root.
  • Artifact delivery resolves only through a validated member key and that member's discovered artifacts.
  • Absolute member paths, boundary escapes, unsafe authorities, and unsafe artifact resolution fail locally.
  • Only the selected root and explicit direct members are loaded.
  • Each valid project is loaded at most once per derived refresh.
  • Process-local derived caching is allowed; persisted or authoritative cache state is not.
  • Aggregate ordering is stable by score, project key, and project-relative path.
  • Federation remains localhost-only under the existing viewer security contract.

Implementation ownership

EnginesRemain project-local and never traverse federation membership during installation.

Acceptance evidence

  1. A project without federation preserves current selection, search, API, viewer, init, and install behavior.
  2. Running inside a member never consults an ancestor federation.
  3. Running at a federation root exposes root and valid direct-member knowledge.
  4. Fixtures retain the minimum specs and shared topology while exercising custom note and compound postmortem record kinds.
  5. Equal IDs and paths across projects remain independently addressable without derived IDs.
  6. Intentional corpus overlap across project topologies remains visible under each project without an ownership diagnostic.
  7. Duplicate member realpaths load once and produce localized maintenance diagnostics.
  8. The failure matrix preserves every safe valid corpus boundary.
  9. Root-to-member links resolve canonically only in the composed view; reverse and sibling links remain bounded.
  10. Unknown member keys, path escapes, symlinked authorities, and unsafe artifact requests cannot expose content.
  11. Search, API, viewer, and the conditional skill reference agree on project ownership and addressing.
  12. An explicitly authorized interaction can update named root and member documents without a federated mutation command.
  13. Performance evidence shows work bounded by the selected root and declared direct members.

Deliberately deferred

  • Automatic discovery of descendant or ancestor relic.yaml files.
  • Transitive federation and cycle handling.
  • Projects outside the selected project boundary.
  • Member-to-root and member-to-sibling federated links.
  • Global or derived document IDs.
  • Automatic cross-project writes, synchronization, reconciliation, or lifecycle governance.
  • A fifth CLI command or a second Relic configuration file.
