Search

Structured search over kind and opaque metadata

Search gains a list of structural filters, by corpus membership and by literal metadata key and value, and its JSON result carries the links each document already has in the read model. Relic still assigns no meaning to any project metadata key or value.

Opaque by construction: a metadata filter is a literal structural match. It never promises that a key exists anywhere, never types a value, and never produces a diagnostic. The project, or a tool built on top of Relic, owns meaning.

Why Relic needs it on its own

Free-text search already reads serialized metadata, but it cannot express "every ADR", "records that carry an owner", or "records tagged auth" without false positives from body text. A project with dozens of declared records needs these narrowing questions with no external tooling. Consumers such as other CLIs and agents gain a stable, read-only way to select documents without parsing the corpus a second time.

Filters

FilterMatches a document when
kind One of its corpus memberships equals the given value: spec, shared, or a record kind declared in topology. Memberships are topology-owned, so this filter is native Relic structure.
key Its top-level metadata contains that key, whatever the value.
key=value The top-level value under key is a scalar whose string form equals value exactly, or is a list containing such a scalar.
  • Every given filter must match. AND is the only combination; there is no OR, negation, range, or ordering. A caller that needs another combination runs several searches and combines the results itself.
  • Filters combine with the free-text query; the query becomes optional when at least one filter is present.
  • Keys are compared exactly. Values compare against the scalar's string form, so priority: 3 matches priority=3. A null value matches only the presence filter.
  • Nested objects, lists of objects, and dotted key paths are not traversed; such values match only the presence filter.
  • A document without the key, or a metadata shape the filter cannot read, simply does not match. No warning, error, or verify finding exists for absence.
  • Specification metadata is whatever the read model already exposes for that specification; no new extraction rule is introduced.

JSON filter input

As an extra form beside key and key=value, a filter argument may be a JSON object. This lets agents and tools build a filter set as one value instead of concatenating repeated options. It is only another spelling of the same filters and adds no matching power.

JSON entryEquivalent filter
"owner": "platform"owner=platform
"priority": 3, "draft": truepriority=3, draft=true, compared by the same scalar string form
"owner": nullowner, presence only
"tags": ["auth", "api"]tags=auth and tags=api
  • An argument is read as JSON when it starts with {; any other argument keeps the key or key=value form.
  • Every entry of the object is one more filter, combined by AND with all other filters, whether they came from JSON or from the plain form. Both forms may be mixed and repeated.
  • Keys are top-level metadata keys, compared exactly; they are never split into paths.
  • Invalid JSON, a root that is not an object, or a nested object or list of objects as a value is an input error of that invocation. It is reported before searching and is not a knowledge diagnostic.

One shape rule in core

The viewer already classifies metadata by value shape, distinguishing scalars, scalar lists, and nested structures, in its metadata component. That classification moves into core and both the viewer and search consume it, so the rule that decides "scalar or list item" exists once. This removes logic held only by the viewer instead of adding a second copy for search.

Metadata values never become graph edges. A frontmatter value that looks like an identity is still opaque text; relationships are authored as ordinary relative links, as decided in ADR-002.

Result model

  • Each document result additionally carries its outgoing links and derived backlinks as the read model already computes them, so a consumer can follow the web without a second query.
  • The JSON output carries a format version. Additive fields keep the version; removed or renamed fields change it.
  • Artifacts have no metadata or membership of their own: any metadata or kind filter excludes them.
  • In a federated view filters apply to every composed document, and results keep their project address.
  • Human output stays focused on results; filters change selection, not presentation.

Command surface

relic search [query...] --kind adr --meta owner --meta tags=auth --json relic search --kind work --meta '{"owner": null, "tags": ["auth", "api"]}' --json

--kind and --meta are repeatable options on the existing search command. The public surface stays at five commands. The local API used by the viewer exposes the same selection through the same core function.

Deliberately absent

No key registry, known-value list, metadata index or cache, type coercion beyond the scalar string form, status vocabulary, saved queries, query language, sorting by metadata, or diagnostics about missing metadata. No metadata value is resolved as a link.

Other logic operators are deferred, not rejected. OR, NOT, and richer value matching are not ruled out. They stay out of this scope because no current user needs them, and caller-side combination covers today's cases. Revisit them when several Relic users need them, or when a consumer's needs change substantially. Design them then as a whole, rather than growing operators one at a time.
